# Changelog
All notable changes to this crate will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

This crate versions and ships independently of the `frensense` binary. It owns
the grammar-facing language specs, the rule cards every reporting surface reads
its prose from, and the severity/CWE tables. The vocabulary *tables* that feed
sink and source matching are generated by `frensense-packgen`.

## [0.8.1]

### Added

- **The node-kind vocabulary the lowering needs, as `LanguageSpec` queries.**
  `classify` answers "what value does this node produce", but the lowering also
  asks placement questions that no `NodeRole` expresses: is this child a
  comment, is this statement a group of variable declarators, is this anonymous
  function a *value* to bind, is this `switch` the statement form the condition
  chain owns, which clause is a case. Each answer was a hardcoded grammar
  spelling inside `frensense-engine` (`"lexical_declaration"`,
  `"arrow_function"`, `"jsx_attribute"`, `"storage_class_specifier"`, the four
  jump kinds), so the engine knew the C, JS, Python, Rust and Go grammars.
  Sixteen predicates and two enums (`JumpKind`, `JsxPart`) now name them; every
  default is `false`/`None` (or `is_comment`'s universal `comment`) and each
  provider states only what its own grammar has, so a language cannot answer
  another language's question. No behaviour change: the overrides reproduce
  exactly the spellings the engine compared, asserted per grammar in
  `providers/node_vocabulary_tests.rs`.

- **The grammar-shape queries the CFG builder and the match-arm evaluator
  ask, as `LanguageSpec` methods.** `classify` cannot answer "is this child
  the body of the loop", because the grammars disagree about fields: the
  builder discovers a loop's body and condition, a branch's condition and
  consequence, and a switch's clauses by walking children and testing their
  kinds. That test was a set of substrings inside `frensense-engine` -
  `contains("statement")`, `contains("block")`, `ends_with("body")`,
  `contains("declarator")`, `contains("update")`, `contains("case")` - plus
  the match-arm pattern vocabulary (`_`, `case_pattern`, `union_pattern`) and
  the literal union the constant evaluator folds. Fifteen methods and
  `LiteralShape` now name them, with the builder's current vocabulary as the
  defaults, so a provider can narrow a shape query for its own grammar without
  the engine learning that grammar. No behaviour change; the defaults are
  pinned in `providers/node_vocabulary_tests.rs`.

- **The parameter-binding grammar tables, moved out of the engine.** The
  harness knew how each grammar spells a parameter: `required_parameter` with a
  `pattern` field, Python's `typed_parameter`/`default_parameter`/
  `list_splat_pattern` wrappers, Rust's `parameter`, C's `parameter_declaration`
  whose declarator may be a `pointer_declarator` around the name, Go's one
  declaration carrying several `name` fields (`a, b string`). Those tables -
  and the C declarator walk that found the list itself - are now
  `LanguageSpec::function_params`, `LanguageSpec::param_bindings` and
  `LanguageSpec::is_self_parameter`. `function_params` follows the
  `NodeRole::Function`'s long-unused `params_field` and keeps walking until a
  `Parameters` node appears, which is what C needs; every other grammar answers
  from its existing field. No behaviour change: the moved tables are verbatim,
  and `providers/node_vocabulary_tests.rs` asserts the bound names for all five
  grammars (grouped Go names, C pointer declarators, Python splats, a TS rest
  parameter, a Rust receiver).

- **`providers::javascript::{JsFamily, JsDialect}`: one extension point for the
  JavaScript family.** JavaScript, TypeScript and a Vue SFC's script blocks are
  one language to this crate — same grammar family, same classification, same
  import/export extraction — but each `<Lang>Spec` used to restate the whole
  grammar-facing contract, so a change to shared behaviour had to be made three
  times. `JsFamily` names only the member's `JsDialect` (extensions, grammar,
  symbol query, `wrap_region`, route decorators — the values that actually
  differ) and receives the complete `LanguageSpec` implementation from a
  blanket impl in `providers/javascript/family.rs`. `preprocess_source` is the
  one overridable step: Vue blanks its markup there. A new single-file
  container (Svelte, Astro) now needs a dialect arm and a `preprocess`, not a
  fourth copy of the ladder.

- **`Severity::parse_label` and `SEVERITY_LABELS`: one vocabulary for
  severity labels.** Corpus metadata, bundle patterns, the bundler's `M003`
  lint, the CLI `--severity` flag and every MCP threshold now parse through the
  same six labels (`critical`, `high`, `medium`, `warning`, `low`, `info`).
  The three-tier ladder is unchanged (`critical` -> `Critical`,
  `high`/`medium`/`warning` -> `Warning`, `low`/`info` -> `Info`), but an
  unknown label is `None` so callers can refuse it; `Severity::parse` keeps its
  documented `Info` fallback for internal callers and delegates to the same
  table. Before this, only the CLI knew three of the labels, `--severity high`
  was a hard error, and an MCP client that passed `high` got `info` (the least
  restrictive floor) with no diagnostic.

### Changed

- **The JavaScript/TypeScript/Vue specs are implemented once instead of three
  times.** `spec_js.rs` (132 lines) and `spec_ts.rs` (168 lines) are now ~25-line
  dialect declarations, and `spec_vue.rs` keeps only its SFC rewrite; the
  duplicated delegate ladder, the two symbol queries and the shared call query
  moved into `family.rs`. No behaviour change: `JavaScriptSpec` still answers
  with the TypeScript call query, Vue still reports
  `fact_language() == "typescript"`, and the crate's 54 unit tests (including
  the module-surface per-language cases) pass unchanged.

- **The remaining cross-provider clones are one implementation each.** Three
  copies of the "public `ModuleItem`s become `Export`s" projection (C, Go,
  Python — plus Rust's `filter_map(rust_export)`, which jscpd could not see
  because it was spelled differently) are now
  `ModuleItem::public_exports`; Python's two identical `aliased_import`
  readers are `python_aliased_names`; and the five open-coded
  `goto_first_child`/`goto_next_sibling`/`goto_parent` walkers (Go, Python,
  Rust and both JS extractors) are `spec::walk_preorder`. C's `struct` and
  `enum` arms, which differed only in the `ItemKind` they pushed, are one arm.
  Both helpers are `pub(crate)`: provider detail, not new contract.
  `jscpd frensense-lang/src -k 60 -l 6` goes from **224 duplicated lines in 12
  clones (3.29%)** to **0 clones (0.00%)**. At the much tighter `-k 40 -l 4`,
  where the crate started at 354 lines / 27 clones, 89 lines / 12 clones remain:
  the per-language `NodeRole` field-name arms (each grammar names its own
  fields), `use` blocks, and three short loops. Those are grammar facts, not a
  shared implementation, and merging them would recreate the hardcoded-node-kind
  problem `LanguageSpec` exists to delete.

## [0.8.0]

### Breaking

- **`NodeRole` gains a variant and its later discriminants shift.**
  `NodeRole::KeywordArgument` (spec.rs:129) is new, inserted before `ClassDef`,
  so every variant from `ClassDef` (25) through `Other` (32) now has a
  discriminant one higher than in `0.7.0`; `NodeRole` is also exhaustive. Both
  are breaking for downstream code that casts a variant to a number or matches
  the enum without a wildcard. `Export` gains `visibility` and `kind` fields.
  `cargo semver-checks check-release --release-type patch` against the published
  `0.7.0` reports 3 major checks failing for exactly these items.

### Added

- **Vue single-file components are now first-class language specs.** The new
  `providers::javascript::VueSpec` answers the `vue` extension; it reuses the
  shared JS/TS AST classification, imports, packages and param-taint
  mechanisms, because an SFC's script blocks are typed TypeScript. There is
  no Vue grammar dependency: the spec's `preprocess` blanks everything
  outside a `<script>` body — template, style sections, the tags themselves —
  into same-length runs of spaces (newlines kept), so the TSX parser sees
  only the script code while every byte offset, line and column still points
  at the original file (the position contract is asserted by tests against
  length, newline layout and findable code offsets). Template-only
  components parse as empty modules; `<script src>` blocks contribute no
  code; multiple script blocks are all kept.
- **`LanguageSpec::preprocess` and `LanguageSpec::fact_language`** are new
  trait methods with identity defaults, so existing provider crates need no
  edit. `preprocess` rewrites source before parsing (see above; the contract
  is offset preservation). `fact_language` is the key the fact tables and
  learned `.frc` knowledge are filed under: the Vue spec delegates to
  `typescript`, since a container spec sharing another spec's grammar shares
  its vocabulary sections too; registry identity still keys on `name()`.

- **Advisory CWE classification**: built-in advisories now carry their canonical
  CWE so findings resolve to a stable CWE identifier instead of a generic label.
- **Rule cards** (`rule_card` module): one card per sink label and built-in
  checker rule holds the stable id, title, CWE list, why and fix, and the
  severity tables resolve through them (`card_by_id`, `checker_key`,
  `cwe_url`, `all_cards`), so no built-in rule can ship without a CWE and the
  terminal, SARIF, JSON and `frensense explain` surfaces cannot drift. Tests
  enforce unique ids, a CWE on every card, and that only fallback cards are
  generic. `frensense` reports the text; this crate owns it.
- **`NodeRole::KeywordArgument`**: keyword arguments (`f(x=1)`, `obj.f(a: 1)`)
  get their own role instead of falling through to `Other`/`Argument`, so a
  spec can classify them as a slot without a node-kind string.
- **CWE-94 tagging for Code Execution**: `eval`, `exec`, and `compile` sinks now
  carry CWE-94 (Code Injection). The mapping previously matched a dead arm - the
  sink slug is `"execution"`, not `"eval"` - so Code Execution findings were
  reported without a resolvable CWE. CWE-94 class TPR moves from 0% to 35%.
- **CWE-601 tagging for Open Redirect**: `redirect`-labelled Resource-role sinks
  now carry CWE-601 (URL Redirection to Untrusted Site). CWE-601 class TPR moves
  from 0% to 61.5%.

### Fixed

- **Python `match` statements classify as `NodeRole::Match`.** The kind was
  listed in both the `NodeRole::Branch` arm and the `NodeRole::Match` arm, and
  the earlier arm won: the `Match` arm was dead code, so `visit_match` never
  ran for Python and a `match` lowered as an `if` whose "consequence" was the
  whole case block. Every arm then executed, and an assignment in an arm that
  can never run (`case 'A': bar = param` when the subject is `'B'`) reached the
  merge and tainted the value read after the `match`. Removing the duplicate
  activates the real lowering, which dispatches on one subject, hoists an arm's
  new bindings (Python scopes them to the function, not the block) and supports
  alternative patterns (`case 'C' | 'D'`). The engine half - folding a subject
  whose value is fixed at compile time - is in `frensense-engine`.
- **The Rust parameter classifier keeps the borrow marker.** `rust_classify_param`
  stripped a leading `&` before matching, so `&Path` compared equal to axum's
  owned `Path<P>` extractor and `&RocketRequest`'s explicit arm was dead. Nothing
  called the hook when that was written; now that `frensense-engine` consults
  `classify_param_taint` while seeding parameter sources, every helper taking a
  filesystem `&Path` (or `&'a Path`) became a taint source - caught by the
  engine's existing `borrowed_path_parameter_is_not_a_source` and
  `borrowed_path_with_lifetime_is_not_a_source` fixtures. The classifier now
  preserves the marker, strips only a lifetime and `mut`, and matches the
  borrowed Rocket request handle explicitly.
