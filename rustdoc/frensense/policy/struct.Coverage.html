Expand description

What a scan covered, as distinct from what it concluded.

“No findings” has two meanings the report used to collapse into one word:

  1. the engine inspected the dangerous operations in this code and no attacker source reached them, or
  2. the engine never looked at the code at all - a file in a language with no spec, a file that failed to lower, or a file where nothing it models as dangerous appeared.

The second is a statement about the engine, not about the code, and printing one verdict for both makes a no-findings scan unfalsifiable. Both are true at once on a large corpus: on the OWASP Benchmark for Python, 622 of 1,230 files yield no recognized sink site.

Every count is derived from data the scan already produces (findings plus ScanTelemetry), so this costs one pass over values the consumer already receives and works on any language. No engine change.

Fields§

§files_found: usize

Source files the walk found: every supported file submitted for analysis plus every source file whose language has no engine spec. The denominator of “N of M files scanned”.

§files_analyzed: usize

Files successfully read, parsed, and lowered.

§files_failed: usize

Supported files that could not be read, parsed, or lowered.

§files_unsupported: usize

Source files dropped without analysis because the engine has no spec for their language.

§sink_sites: usize

Distinct sink call sites the engine recognized (file, line, sink). Every verdict counts: a recognized site is one the engine reasoned about, whether or not it produced an advisory.

§files_with_sink_sites: usize

Analyzed files that yielded at least one recognized sink site.

§files_without_sink_sites: usize

Analyzed files that yielded none. For these, “no findings” describes the engine’s vocabulary, not the code.

§no_sink_files: Vec<String>

First COVERAGE_SAMPLE such files, sorted.

§unresolved_sites: usize

Distinct sink sites whose walk ended Unknown.

§unresolved_sample: Vec<UnresolvedSite>

First COVERAGE_SAMPLE unresolved sites, sorted by file/line/sink.

impl Coverage

Source

pub fn from_scan( result: &ScanResult, considered: &[String], files_unsupported: usize, ) -> Self

Derive coverage from one scan’s findings and input accounting.

considered is the set of paths the runner submitted for lowering; it is only used to name files for the sample, never to count them (the scan’s own scanned count is authoritative). files_unsupported is the number of source files the walk skipped because their language has no spec - the runner knows it from its collected-file list, the engine telemetry does not.

Source

pub fn with_excluded(self, excluded: &[ExcludedPath]) -> Self

Record what the default exclusion rules skipped. Source files inside excluded paths join the denominator (files_found) and count as not analyzed, so a scan that skipped real code cannot read as complete.

Source

pub fn files_excluded(&self) -> usize

Source files the walk found but never analyzed because a default exclusion rule skipped their directory or the file itself, as distinct from files that failed and files whose language has no spec.

Source

pub fn files_not_analyzed(&self) -> usize

Source files the scan found but did not analyze: unsupported languages, read/parse/lower failures, and files the default exclusion rules skipped. The “M - N” in “N of M files scanned”.

Source

pub fn merge(&mut self, other: Coverage)

Fold one scan’s coverage into a running total. Multi-path and --diff-only runs scan one file at a time, so their report is the union, not the last run’s numbers.

Source

pub fn recognized_anything(&self) -> bool

True when the scan recognized at least one sink site somewhere. A scan that recognized nothing has no basis to describe the code.

Source

pub fn fully_resolved(&self) -> bool

True when every sink site the scan recognized was decided.
